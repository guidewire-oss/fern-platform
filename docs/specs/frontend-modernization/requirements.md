# Spec: Frontend Modernization — Requirements

**Status:** Draft
**Owner:** TBD
**Related:** [RFC-004](../../rfc/rfc-004-frontend-modernization.md)
**Created:** 2026-05-14

## 1. Context

The Fern Platform UI is a single 8,787-line `web/index.html` that loads React,
ReactDOM, Babel-standalone, and D3 from `unpkg.com` and transpiles JSX in the
browser. There is no type system, no build pipeline, no component layer, no
component-level tests, no server-side filtering of list views, and no
virtualization for large result sets. Recent UI fixes (#144, #154, #164, #170)
each required hand-editing the monolith with no safety net.

This spec defines requirements for replacing it incrementally without
breaking existing client integrations.

## 1a. Compatibility principle (non-negotiable)

This change **shall not break any existing user**. The constraint applies
to three audiences:

- **Existing API clients** (CI integrations using `fern-ginkgo-client`,
  `fern-junit-client`, `fern-jest-client`, and any hand-rolled REST/GraphQL
  callers). Their code keeps working with **zero edits** through the entire
  migration and for **at least 12 months** after v2 GA.
- **Existing UI users.** When they navigate to a URL they have bookmarked,
  they land on a page that does the same thing it did before — either the
  legacy page (during migration) or a v2 page that has been validated for
  parity (after cutover).
- **Existing operators** (people running self-hosted Fern). They can upgrade
  to a release that ships both v1 and v2 without changing environment
  variables, ingress rules, or database state.

**New users** consume v2 directly: the latest install instructions, the
latest API namespace (`/api/v2`), the latest UI. They are never asked to
learn v1.

**Existing users** receive a **migration guide** (deliverable in this spec)
that explains what changed, what they need to do, by when, and what
automated tools (if any) help them.

Compatibility is enforced by:
- Frozen v1 contract tests (golden files) that fail CI on any v1 response
  diff.
- A schema-diff CI step that fails any GraphQL change that removes or
  retypes a non-deprecated field.
- A migration-readiness checklist (see [migration-guide.md](./migration-guide.md))
  reviewed before each phase exit.

## 2. User stories

- **U1.** As a contributor, I want to change a single dashboard component
  without reading 8,000 lines of HTML, so that small fixes take minutes
  instead of hours.
- **U2.** As an SRE, I want to filter a 1,000,000-row test-run list by
  project, branch, status, tag, and date range and get a result in under
  a second, so that incident triage is fast.
- **U3.** As an SRE, I want to share a URL that reproduces my filter view,
  so that I can hand off triage without screenshots.
- **U4.** As a developer, I want field renames in the GraphQL schema to
  break the build, not the user, so that runtime "blank screen" bugs stop.
- **U5.** As a user, I want test-run pages to render in under 1.5 seconds
  even when a run has 5,000 specs, so that I am not waiting on the UI.
- **U6.** As an operator of an existing `fern-junit-client`, I want my CI
  integration to keep working without code changes for at least 12 months,
  so that I am not forced into an emergency upgrade.
- **U7.** As a frontend dev, I want HMR-fast local dev with the Go backend
  proxied, so that I can iterate in seconds.
- **U8.** As a user, I want a saved view of my common filters that follows
  me across browsers, so that I do not rebuild it every morning.

## 3. Functional requirements (EARS)

### Build, packaging, deploy

- **FR-1.** The system **shall** provide a Vite + TypeScript build that
  produces hashed, minified ES module bundles in `web/dist/`.
- **FR-2.** The Go binary **shall** serve the built frontend from `embed.FS`
  (`internal/web/embed.go`) so the deploy artifact remains a single binary.
- **FR-3.** When a request does not match an API route, the server **shall**
  return `index.html` to support SPA routing.
- **FR-4.** The build **shall** fail when `tsc --noEmit`, `eslint`, or
  Vitest tests fail.

### Frontend stack

- **FR-5.** The application **shall** be written in TypeScript with `strict: true`.
- **FR-6.** All GraphQL operations **shall** be authored as `.graphql` files
  and consumed via typed hooks generated by `@graphql-codegen/*`.
- **FR-7.** Styling **shall** use Tailwind CSS; no CSS-in-JS runtime
  libraries are permitted.
- **FR-8.** Icons **shall** be tree-shakable (`lucide-react`); FontAwesome
  and the inline emoji fallback **shall** be removed.

### Filtering and lists

- **FR-9.** Every list view (projects, test runs, suites, specs, flaky tests,
  tags) **shall** apply filters on the server, not the client.
- **FR-10.** Every list view **shall** support cursor-based pagination with a
  default page size of 50 and a maximum of 200.
- **FR-11.** Every list view **shall** persist its filter state in the URL
  query string, such that pasting the URL reproduces the view.
- **FR-12.** When a user opens a list page without parameters, the default
  query **shall** return ≤ 100 rows and respond in ≤ 250 ms (P75) on a
  1 M-row seeded dataset.
  - *Implementation note:* the v2 test-runs handler also clamps the
    default window to the last 7 days when neither `from` nor `to` is
    supplied, which is the mechanism by which the latency bound is
    achieved at the seeded scale. The clamp can be bypassed with
    `?allTime=1`. See RFC-004 Appendix B.2.
- **FR-13.** When a list response would contain > 100 rows, the UI **shall**
  virtualize the rendered rows such that no more than 100 are in the DOM.
- **FR-14.** Filter facets (counts per facet value scoped to the current
  filter) **shall** be returned in the same response as the list page.
  - *Implementation note:* `byStatus`, `byBranch`, and `byProject` always
    run. The tag facet (`byTag`) is opt-in via `?facets=tag` (the front-end
    auto-opts in when the user expands the Tag section or already has
    tags selected) because the suite_runs→suite_run_tags→tags join is
    expensive at scale. See RFC-004 Appendix B.3.
- **FR-15.** Users **shall** be able to save named filter views, scoped to
  their account, retrievable across sessions and devices.
- **FR-15b.** The Test Runs list (`/v2/test-runs`) **shall** match v1's
  column set: Project, Run ID, Branch, Test Results (passed/failed/skipped
  triple), Status, Duration, Started. Run ID **shall** be its own column
  (not a subtitle of Started) so operators can scan by run identifier.

### Heavy views

- **FR-16.** The treemap **shall** render three drill levels —
  **projects** at the top, **suites** within a project, and **specs**
  within a suite — on user click. Each level **shall not** render
  more than 500 nodes at a time. Spec-level aggregation **shall** be
  ordered by total duration descending so the 500-cap clips the
  cheapest specs first. The treemap **shall** be reachable from the
  Test Summaries page's Tree view toggle; there **shall not** be a
  separate `/v2/treemap` route (consolidated into Summaries to avoid
  duplicate entry points to the same component).
- **FR-17.** Test-run detail **shall** match v1's drill navigation:
  a *Suites* table (columns: Suite Name, Test Results P/F/S, Status,
  Duration, Tags) with each row drilling into a *Specs* table (columns:
  Test Name, Status, Duration, Error Message, Tags, Started). A
  run-level header above both views shows the project, run ID, branch,
  status, environment, commit, run-level tags, the four stat cards
  (Total / Passed / Failed / Skipped), and an optional collapsible
  Metadata panel. Stack traces, retry counts, and flaky markers
  surface inline on spec rows.

### Test Summaries — v1 parity

These requirements close the remaining parity gap between the v1 Test
Summaries page and the v2 trend-card grid. The window selector and per-card
sparkline (trend chart) ship; the stat shape, history affordance, and
view-mode toggle do not yet.

- **FR-17a.** Each project card on `/v2/test-summaries` **shall** display
  three primary counters for the selected time window: **Total tests**,
  **Passed tests**, and **Failed tests**. Skipped is shown when non-zero but
  is not a primary counter. Counters **shall** come from the existing
  `/api/v2/test-runs/trends` aggregate response — no new fan-out per card.
- **FR-17b.** Each card **shall** expose a **View history** affordance that
  navigates to the project's existing test-run history view filtered to the
  same window. The affordance **shall** be a single click target with a
  visible label (not icon-only).
- **FR-17c.** The Test Summaries page **shall** offer a **view mode** toggle
  with two modes — **Card view** (the current trend-card grid) and **Tree
  view** (the v1 treemap, sized by total tests, coloured by pass-rate band).
  The selected mode **shall** persist via the existing user-preferences
  endpoint (`defaultTestSummariesView`) so it survives reloads.
- **FR-17d.** Tree view **shall** reuse the existing `/treemap` aggregate
  endpoint (FR-16, RFC-004 Appendix B.4) and **shall not** introduce a
  parallel aggregate path; the same 60-second result cache applies.
- **FR-15a.** Every page that lists projects (Projects, Test Summaries,
  Dashboard) **shall** auto-paginate the GraphQL `projects` query so the
  page-level filter bar operates over the full project set the user can
  see, up to a hard cap of 500 (matching FR-16's treemap node cap so
  the two views stay consistent). When the cap truncates the visible
  list, a banner **shall** tell the user how to narrow the set.
- **FR-17f.** A `/v2/manager-dashboard` route **shall** preserve the v1
  bookmark by redirecting authenticated manager / admin users to
  `/v2/summaries?view=tree&favoritesOnly=true`. Users without the
  manager or admin role **shall** see a "Manager access only" message
  rather than the redirect. The route **shall not** introduce a new
  page component — it composes existing Summaries state via URL
  search params (`view`, `favoritesOnly`).
- **FR-17g.** The Test Summaries page **shall** honor `view` and
  `favoritesOnly` URL search params on first mount as initial state
  overrides, taking precedence over sessionStorage. Deep-links from
  `/v2/manager-dashboard` (or anywhere else) **shall** land in the
  intended state regardless of the user's last-seen preferences.
- **FR-17h.** The sidebar navigation **shall** filter items by role.
  A "Manager dashboard" entry **shall** appear only for users with
  `manager` or `admin` role; admin-only entries (Users, Admin
  overview) **shall** be hidden from non-admins.
- **FR-17e.** The project detail / "View history" view **shall** render a
  stacked area chart of **Passed / Failed / Skipped** test counts across
  the project's most recent runs (up to 20, oldest-to-newest on the X
  axis). When every run shares the same total, the chart **shall** draw a
  reference line at that total. Hovering a data point **shall** reveal a
  tooltip with run date, the per-status counts, total, and pass-rate.
  The chart **shall** be fed by the already-fetched
  `/api/v2/test-runs?project=…&first=20` payload — no additional request.

### API surface

- **FR-18.** A new REST namespace `/api/v2/*` **shall** be introduced for
  endpoints whose request or response shape changes to support the new
  filter contract.
- **FR-19.** The existing `/api/v1/*` endpoints **shall** remain functionally
  unchanged for at least 12 months from v2 release.
- **FR-20.** All `/api/v1/*` responses **shall** include a `Deprecation`
  header and a `Sunset` header (RFC 8594) once v2 ships.
- **FR-21.** The GraphQL schema **shall** evolve additively. Removed fields
  **shall** be marked `@deprecated(reason: "use X")` for at least one
  release before deletion.
- **FR-22.** Test-result ingestion endpoints used by `fern-ginkgo-client`,
  `fern-junit-client`, and `fern-jest-client` **shall not** change shape in
  v1 during the migration.

### Authentication

- **FR-23.** The new UI **shall** integrate with the existing Keycloak OAuth
  flow without changes to the auth provider configuration.
- **FR-24.** The UI **shall** render an auth skeleton while authentication
  state resolves, suppressing the "error flash" observed in issue #164.
- **FR-24a.** The top-bar **shall** display the authenticated user's name,
  avatar (or initials when no `profileUrl`), role badge, and a Sign-out
  control whenever `currentUser` is non-null. When `currentUser` is null
  the chrome **shall** show a Sign-in affordance pointing at `/auth/start`.
  The user pill **shall** link to the in-app Profile page (no separate
  dropdown menu — clicking the pill navigates).
- **FR-24b.** Sign-out **shall** call `POST /auth/logout`, follow the
  returned `logout_url` to the IdP's end-session endpoint, and fall back
  to `/auth/login` on any failure. The control **shall** be hidden when
  the synthetic `dev-admin` principal is in effect (`AUTH_ENABLED=false`)
  since no provider session exists to terminate.
- **FR-24c.** The Profile page **shall** query only `User` fields that
  exist on the GraphQL schema (`id`, `userId`, `email`, `name`,
  `firstName`, `lastName`, `role`, `profileUrl`, `groups`, `createdAt`,
  `lastLoginAt`) and **shall not** request fields the server does not
  define (gqlgen rejects the whole query on an unknown selection).
- **FR-24d.** The Profile page timezone picker **shall** offer every
  IANA zone the host reports via `Intl.supportedValuesOf('timeZone')`,
  with the browser's detected zone listed first followed by UTC; no
  arbitrary truncation of the list.
- **FR-24e.** The TopBar identity surface **shall** present a
  toggle-able dropdown menu (not a one-way link). Clicking the user
  pill **shall** open the menu; clicking the pill again, clicking
  anywhere outside, or pressing `Escape` **shall** close it. The menu
  **shall** show the user's name, email, and role badge, plus links to
  the Profile page, an Admin Panel (only when role is `admin`), and a
  Sign-out action (subject to FR-24b's dev-admin exemption).

### Migration safety

- **FR-25.** The new UI **shall** mount at `/v2/*` during migration; the
  legacy UI **shall** remain reachable at `/` until parity is verified.
- **FR-26.** Each migrated page **shall** ship with at least one Playwright
  test covering its golden path before the legacy page is removed.
- **FR-27.** No release in this spec **shall** require an existing user to
  change their client-library version, environment variables, database
  configuration, OAuth settings, or ingress configuration as a precondition
  for upgrading.
- **FR-28.** Every release that introduces or changes a public-facing
  contract **shall** be accompanied by a corresponding update to
  [migration-guide.md](./migration-guide.md) and the
  `docs/developers/migrate-v1-to-v2.md` document shipped to users.
- **FR-29.** Database migrations introduced by this spec **shall** be
  forward-only and **shall** support a one-release rollback. Index
  creation **shall** use `CREATE INDEX CONCURRENTLY`. New tables and
  columns **shall** be nullable or have defaults. No column rename or
  drop is permitted during the migration window.
- **FR-30.** The Go binary **shall** read configuration from the same env
  vars and config-file keys as before; new keys **shall** have safe
  defaults. Setting `FERN_V2_UI_ENABLED=false` **shall** restore the
  pre-v2 user experience byte-for-byte.

## 4. Non-functional requirements

### Performance budgets

| Metric | Budget |
|---|---:|
| Initial JS bundle (gzip) | ≤ 150 KB |
| Per-route async chunk (gzip) | ≤ 80 KB |
| Total app bundle (gzip) | ≤ 600 KB |
| First Contentful Paint (P75, broadband) | ≤ 1.0 s |
| Time-to-Interactive (P75) | ≤ 1.5 s |
| Test-run list server response, default filter (P75, 1 M rows) | ≤ 250 ms |
| Test-run detail server response, 5 K specs (P75) | ≤ 400 ms |
| Treemap top-level server response (P75) | ≤ 300 ms |

### Quality

- **NFR-1.** Vitest unit test coverage of `web/src/lib/**` and
  `web/src/features/**/hooks/**` shall be ≥ 80 % statements.
- **NFR-2.** Playwright suite shall cover at least 12 golden-path scenarios.
- **NFR-3.** A CI job (`size-limit`) shall block merges that exceed the
  bundle budgets above.
- **NFR-4.** TypeScript shall compile with zero errors and zero `any` in
  application code (codegen output exempt).

### Accessibility

- **NFR-5.** All interactive components shall meet WCAG 2.1 AA contrast and
  keyboard-navigation requirements (enforced via `@axe-core/playwright`).

### Security

- **NFR-6.** No third-party CDN shall serve application JavaScript at runtime.
  All dependencies shall be vendored via `pnpm install` and bundled.
- **NFR-7.** A strict Content Security Policy header shall be emitted by the
  Go server for all HTML responses.

### Operability

- **NFR-8.** A single `make deploy-all` (or successor) shall continue to
  produce a working deployment end-to-end.
- **NFR-9.** The frontend build shall run in CI in ≤ 90 seconds on the
  standard runner (cold pnpm cache).

## 5. Out of scope

- Server-side rendering and meta-frameworks (Next/Remix).
- Mobile-native clients.
- Internationalization (deferred; structure shall be i18n-ready).
- Dark mode (CSS-variable tokens prepared; theme switch deferred).
- Redesign of any visual element — parity first.

## 6. Acceptance criteria

This spec is satisfied when **all** of the following are true:

- [ ] `web/index.html` (legacy) and `web/js/*.js` (legacy) are deleted from
  `main`.
- [ ] The Go binary is the sole deploy artifact and embeds the compiled
  frontend.
- [ ] All migrated pages have Playwright golden-path coverage running in CI.
- [ ] The performance and bundle budgets defined above are enforced and
  passing in CI.
- [ ] `/api/v2/*` exists, is documented in `docs/developers/api-reference.md`,
  and is used by the new UI.
- [ ] `/api/v1/*` endpoints used by published client libraries pass the
  existing acceptance tests without modification.
- [ ] GraphQL schema diffs in CI fail builds that delete a non-deprecated
  field.
- [ ] [migration-guide.md](./migration-guide.md) is published and linked
  from `README.md`, `CONTRIBUTING.md`, and every deprecated v1 endpoint's
  response (`Link` header pointing at it).
- [ ] An automated `fern migrate check` CLI command (or equivalent) reports
  which v1 calls a given client is still making, so operators can verify
  migration completeness before the v1 sunset date.

## 7. Open questions

- **OQ-1.** Router choice: TanStack Router vs React Router 6 — finalize in
  Phase 0 of [tasks.md](./tasks.md).
- **OQ-2.** Package manager: confirm `pnpm` is acceptable to the
  organization (vs `npm`).
- **OQ-3.** Auth: does Keycloak need PKCE flow adjustments to support the
  Vite dev server origin (`:5173`)? Verify before Phase 1.
- **OQ-4.** Saved views: store as JSON in Postgres on `users` table, or
  introduce a `saved_views` table? Lean toward the latter for indexability.
- **OQ-5.** Should `/api/v1` enter sunset on a date or on the next major
  release? Recommend date (12 months from v2 GA) so client-lib owners can
  plan.
